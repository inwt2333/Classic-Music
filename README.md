# 古典音乐演出与作品指南

一个连接经典作品与国内现场演出的静态 Web 应用。项目从场馆和乐团官网自动采集未来演出，统一展示列表、日历、节目单、票价和来源；同时通过独立的规范知识层，为经典作品提供导赏、结构、聆听提示、录音建议和近期现场入口。知识内容由人工维护条目和带证据、带风险评分的 DeepSeek 自动条目共同组成。

当前重点是验证四件事：

1. 不依赖人工录入，能否稳定采集不同官网的演出数据。
2. 能否正确区分作品、乐章、人物、场馆与厅堂。
3. 数据能否支持按日期、场馆、曲目和音乐家检索。
4. 规范作品知识能否与官网节目单可靠匹配，形成“演出 → 作品指南 → 近期演出”的双向导航。
5. 账号身份能否在不改变静态内容发布架构的前提下，为个人偏好同步和受控审核打下基础。

知识库已发布 13 位作曲家和 50 部作品，其中 36 部为首批人工维护内容，14 部由无人值守流水线自动生成。完整开发计划见 [TODO.md](./TODO.md)。

## 当前能力

### 前台

- 未来演出列表和月历视图；前台不再展示历史演出。
- 支持本周、周末和本月快速筛选，所有快速筛选都可再次点击取消。
- 支持城市、场馆、乐团、演出类型和是否有节目单的组合筛选。
- 支持按演出时间、最近更新、最低票价和节目单完整度排序，并可在账号中保存最多 12 组常用筛选方案。
- 搜索标题、曲目、作曲家、人物、乐团和场馆；支持“马五”等常见简称别名；筛选与当前选中项目同步到 URL。
- 展示场馆与具体厅堂，避免把“东方艺术中心”和“东方音乐厅”等层级混淆。
- 列表直接展示核心曲目、主要人物、票价和售票状态。
- 展示完整节目单，并把大作品下的乐章、作词、编曲和改编等署名从曲目标题中分离展示。
- 展示票价档位、演出简介、指挥、演奏者和数据来源。
- 点击作品、人物或乐团进入实体视图，查看别名和相关演出；点击场馆进入场馆视图并可打开地图。
- 支持单场演出加入日历、当前筛选结果导出 `.ics`、一键复制演出信息。
- 支持登录后标记“想去”和“已购”并按个人状态筛选；状态与必要演出快照同步到 Supabase，已购音乐会过期后仍保留在个人页。
- 支持关注音乐家、作品、乐团和场馆；关注、提醒历史、已读/删除状态会跨设备同步，采集变化命中关注对象时在站内提醒中心展示。
- 支持 Supabase 邮箱密码注册与登录、找回/修改密码、会话恢复和退出登录；用户名作为站内显示名称，账号与管理员角色由受 RLS 保护的独立数据表维护。
- 当前关闭注册邮箱确认，用户提交邮箱和密码后立即创建账号；找回密码仍需要邮件服务，配置自定义 SMTP 前不保证外部邮箱能够收到重置邮件。
- 关注、想去、已购、提醒和保存筛选均要求登录，并由 Supabase RLS 按用户 ID 隔离；首次登录自动合并旧的本机记录，离线修改会在恢复连接后补交。
- 审核入口只对管理员账号显示，直接访问审核地址也会再次验证身份与角色；GitHub Pages 上的远程写入审核仍保持关闭。
- 登录后的个人页集中展示账户资料、按作品/音乐家/乐团/场馆分类的关注内容、想去与已购演出及保存的筛选方案；这些数据可跨设备恢复，已购演出退出未来列表后继续以历史记录展示，管理员可从个人页进入本地审核工作台。
- 支持生成包含时间、地点、票价、人物、乐团、核心曲目和购票二维码的演出分享卡片，并直接复制到剪贴板；受限浏览器会回退为下载 PNG。
- 详情页对可能不完整的信息给出简明提示，并允许用户报告错误、跳转到预填好的 GitHub 纠错单；采集方式、模型评分和内部处理状态不向普通用户展示。
- 提供变化历史页，持续保存采集产生的新增、下架、延期、取消和票价变化，并展示变更前后的具体差异；曲目与演出人员变化因官网排版、OCR 和解析波动较大，不写入历史。
- 提供独立的产品更新日志，按发布日期记录网站功能、体验改进和问题修复；移动端通过顶部“更多”菜单访问数据来源、变化历史和更新日志。
- 从曲目跳转到 B 站、IMSLP、MusicBrainz 和中文资料搜索；录音建议优先提供经过核实的直接来源。
- 桌面端顶部与演出列表随页面滚动，详情栏悬浮并独立滚动；移动端使用筛选抽屉和全屏详情，月历在 320px 窄屏仍保持完整七列并通过场次角标承载密集日期。
- 首页只读取轻量索引，演出和知识详情按需加载；日历代码按视图懒加载。
- 视觉使用克制的音乐会节目册配色、衬线标题和少量谱线/音符纹样，在桌面与手机端保持简约、清晰和可扫描。

### 作品知识库 MVP

- 规范知识内容独立维护，不从未来演出实体反向生成；作品即使没有近期演出也继续发布。
- 节目项保留从官网文本生成的兼容性 `workId`，并可通过人工审核或通过确定性身份校验的精确规则关联永久 `knowledgeWorkId`；修改译名或标题不会改变规范作品 URL。
- 只有官网或人工确认的节目项能够命中知识映射；未经确认的 OCR、AI、标题推断和歧义候选不会自动展示知识结论。
- 经审核映射的曲目在演出详情中显示“了解作品”，并直接提供一句听前摘要、预计时长、入门等级和关键标签；作品和作曲家分别使用稳定的 `?work=...`、`?composer=...` 地址。
- “作品库”当前展示 50 部作品和 13 位作曲家，分为探索、精选、作曲家和作品四个视图；首页连接近期现场、入门作品、音乐史时期和体裁大类，目录支持标准时期、体裁、作曲家及聆听门槛筛选。
- 精选页根据当前知识映射和未来演出自动生成“经典作品正在上演”“适合作为起点的现场”“管弦乐”“协奏曲”“室内乐”和“两百元以内”等专题，支持城市与未来 30/90 天筛选及可分享 URL。
- 知识索引在构建时将自由文本时期与具体体裁归一为稳定的 `periodKey` 和 `genreFamily`，新生成条目与人工条目共用同一套分类规则。
- 作品页展示规范名称、导赏、聆听点、乐章结构、配器、录音建议、相关作品、来源、审核时间和已匹配的近期演出，并可从作品页返回演出详情或原精选专题。
- 作品和作曲家页均可直接关注；作曲家页展示简介、时期、风格、代表作品和由已审核作品汇总的近期演出，后续新演出或数据变化沿用现有站内提醒体系。
- 当前未来演出中有 48 个节目项精确关联到 30 部规范作品。没有近期演出的作品仍可独立访问并显示明确的暂无演出状态。
- 高质量乐团官网的新作品可由独立任务自动发现、检索证据、调用 DeepSeek 生成和复核、评分并发布；低分、乐章、选段、身份冲突和低置信提取结果自动跳过。
- 当前阶段尚未完成异常映射审核队列、作品收藏、个性化推荐和完整听前准备页。

### 数据采集

- 每个官网使用独立 adapter，禁止跨站复用页面区块识别规则。
- 优先调用官网公开接口，保存列表、详情和票价原始 JSON 快照。
- 回归测试所需的最小真实响应 fixture 提交在 `scripts/fixtures/`，测试不依赖本机采集缓存。
- 上海东方艺术中心支持多种节目单排版以及按演出日期分组的节目。
- 上海音乐厅支持编号、双语、作曲者分组、词曲/改编说明和同名不同作品号曲目。
- 苏州交响乐团支持乐季、特别策划等栏目，以及一页多日期、多时间场次。
- 国家大剧院、中国交响乐团、中国爱乐乐团和上海爱乐乐团均使用各自独立的列表发现与详情解析规则。
- 跨来源去重联合比较时间、标准化场馆/厅堂、标题、艺术家与曲目，并保留全部官网来源链接。
- 星海音乐厅等场馆来源会把场馆与具体厅堂分开保存，并清理官网附加在演出标题末尾的场馆名称。
- 纯图片节目单优先使用通义千问视觉模型识别；接口不可用时自动回退到本地 Tesseract.js OCR。
- OCR 或正文仍不足以还原节目单时，详情页按需展示官网原始节目单图片，供用户直接核对，不把普通演出照片误当作节目单证据。
- 微信公众号文章支持半自动导入：链接尽力读取、正文粘贴回退、多场候选拆分、可编辑审核和人工确认后发布。
- DeepSeek 节目单提取仍是实验性兜底；独立的知识扩充任务已启用严格证据与评分门槛。
- 采集结果支持保守的跨来源合并、稳定 ID、排序和数据质量审计。
- 节目单会统一清理曲目尾部的作词、作曲、编曲、改编、原曲和民歌来源等署名；来源适配器与保守质量层还会排除“注/说明/备注”、演出人员、伴奏人员、介绍正文和推荐卡片，避免把它们误当作品。
- 每次采集输出新增、下架、延期、取消和票价变化；曲目与演出人员继续刷新但不进入变化历史，来源失败也不会被误判为下架。

## 技术栈

- React 19 + TypeScript + Vite
- Node.js 22.14+
- Cheerio
- Zod
- Tesseract.js
- QRCode
- Node.js 内置 SQLite
- GitHub Actions + GitHub Pages
- Supabase Auth + PostgreSQL RLS（账号身份、角色与个人数据）

采集后的标准化数据写入本地 SQLite，随后导出适合静态托管的 JSON，演出与知识内容仍不需要常驻后端。Supabase 负责注册验证、密码登录、用户资料、管理员角色，以及想去/已购演出快照、关注、提醒状态和保存筛选的私有同步；所有个人表均启用 RLS。浏览器保留按账号分区的本地缓存与离线待同步队列，不作为唯一数据源。

## 快速开始

安装依赖：

```bash
npm install
```

直接使用仓库中的数据启动前端：

```bash
npm run dev
```

打开 [http://127.0.0.1:5173/](http://127.0.0.1:5173/)。

### 配置账号系统

将 `.env.example` 中的两个 Supabase 前端变量写入不会提交的 `.env.local`：

```text
VITE_SUPABASE_URL=https://你的项目 ID.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=你的 Publishable Key
```

在 Supabase SQL Editor 中依次执行 [`supabase/migrations/202608100001_user_identity.sql`](./supabase/migrations/202608100001_user_identity.sql) 和 [`supabase/migrations/202608100002_personal_events.sql`](./supabase/migrations/202608100002_personal_events.sql)，确认 Authentication 的 Email provider 已启用并关闭 Confirm email；再运行 `npm run auth:verify` 检查账号服务、个人数据表、匿名隔离、匿名写入和管理员函数权限。首次注册并登录后，可按 [`supabase/README.md`](./supabase/README.md) 将指定账号提升为管理员。Secret Key、Service Role Key 和用户角色不得放入任何 `VITE_` 变量。

重新采集数据并启动：

```bash
npm run scrape
npm run dev
```

采集需要能够访问对应官网。采集失败不会阻止其他来源继续执行，错误会记录到结果文件的 `stats.errors`。

## 常用命令

| 命令 | 用途 |
| --- | --- |
| `npm run dev` | 启动本地开发服务器 |
| `npm run build` | TypeScript 检查并构建前端 |
| `npm run auth:verify` | 验证 Supabase Auth、账号与个人数据表、匿名隔离及管理员函数权限 |
| `npm run scrape` | 采集全部来源；对“正文无曲目且含详情图片”的候选项目执行轻量 OCR 初扫 |

| `npm run scrape:ai` | 启用实验性的 DeepSeek 结构化兜底 |
| `npm run reviews:apply` | 重新应用人工审核文件并重建静态数据与 SQLite |
| `npm run knowledge:dry-run` | 统计可信官网中未映射的作品，并预览已有作品映射与生成队列 |

| `npm run test:parser` | 运行全部来源 adapter 与 OCR 提取器的回归测试 |
| `npm run test:data` | 测试跨来源合并、稳定 ID、知识映射与发布、人工审核和变更检测 |

统一演出数据结构定义在 `src/types.ts`，规范知识结构定义在 `src/knowledge/types.ts`。SQLite 将来源记录、演出、场次、场馆、人物、组织、作品、节目单、票价、字段观察和审核项拆分存储；静态导出仍保留前端需要的聚合结构。

### 作品身份与发布

节目单中的 `workId` 是由作曲家、标题和作品号文本生成的兼容性标识，用于现有实体关联、筛选和关注；译名或元数据改变时，它也可能改变。规范层的 `knowledgeWorkId` 是不依赖展示名称的永久标识，用于作品内容和公开 `?work=` URL。

`scripts/knowledge-store.ts` 使用 Zod 校验永久 ID、实体引用、来源、发布状态和映射歧义。构建过程应用 `reviewed-exact` 和通过自动身份校验的 `automated-exact` 映射，并从未来已发布演出计算 `upcomingEventIds`；没有近期演出不会使知识作品退出索引。

### 自动知识扩充

自动任务只读取 `knowledge/automation.json` 中允许的高质量来源。目前启用上海交响乐团、中国交响乐团和中国爱乐乐团。范围严格按演出记录中的 `sources[].sourceId` 判断，与 `ensemble` 字段无关：因此上海交响乐团官网发布的客座乐团、独奏会、室内乐等演出同样进入候选；反过来，其他来源仅把演出团体写成“上海交响乐团”也不会因此获得信任。候选必须来自官网节目单且置信度为 `official` 或 `manual`；OCR、AI 提取和标题推断不会进入自动发布。

流水线先以作曲家、标题和作品目录号匹配现有知识。未命中时按“作品身份解析 → 使用标准英文名检索证据 → 完整详情生成/缺失字段补全 → 独立审计”处理。候选排序不再奖励已有作曲家，并在同等优先级下先处理更早发现的条目，避免现有十二位作曲家长期占据队列。若作品的作曲家尚未入库，任务会额外检索人物资料；只有独立的非官网人物证据支持身份和所填传记字段时，才会同时建立作曲家档案。

联网检索由本地任务完成，而不是假设模型自带浏览器：任务主动读取演出官网、英文/中文 Wikipedia、Wikidata、MusicBrainz 和 Apple Music，再把带固定 ID 的证据交给 DeepSeek。Wikipedia 原始配器章节会单独清洗，避免模板列表在纯文本接口中丢失。生成与审核规则见 [DeepSeek Skill](./skills/deepseek-knowledge-curator/SKILL.md)。模型不能生成 URL、永久 ID、状态、风险分数或不存在的证据 ID。

知识库任务使用 `deepseek-reasoner`。音乐资料的覆盖和可追溯性仍由上述宿主联网检索保证。程序会兼容模型偶发的字段层级偏移和空标签，移除没有真实录音证据支持的推荐，并把证据不足的作品降为待补全或直接拦截，不会为追求完整度伪造事实。

评分达到 90 且标题、体裁、年代、时长、详细配器、导赏、乐章、聆听点和录音均完整时标记为完整条目；达到 70 的基础条目可先发布，但会进入持续补全队列并在七天后重试。Skill 升级也会重新检查旧自动条目。升级采用按字段合并和分数优先策略，低分、空字段或较短配器不能覆盖已有的更好内容。低于 70、证据冲突或不是完整作品时自动跳过。每个自动条目保存模型、Skill 版本、提示词散列、来源演出、证据和分数，人工内容不会被自动任务覆盖。

### 变更历史

每次采集先对比上一份完整数据集，再把新增、下架、改期、取消、阵容和票价变化合并到 `public/data/changes.json`。文件不会被最新一批结果覆盖；同一变更 ID 会自动去重，并记录每次采集的时间和变更 ID。变更条目保存当时的演出摘要及变更前后快照，因此演出下架后仍可查询标题、时间、场馆、票价和阵容。前台会直接显示旧值到新值，以及人员的删除项和新增项。

“变化历史”页面支持按关键词、变化类型、起止日期和本次采集筛选，结果按检测日期倒序并分批渲染。旧版仅包含 `generatedAt` 和 `changes` 的文件会在下次采集时自动迁移到历史格式。SQLite 的 `changes` 与 `scrape_runs` 表继续保留完整本地记录。

人物和乐团的变更比较会先统一基础格式。曲目及乐章仍会随官网重新采集并更新到演出详情，但不参与变化历史和关注消息，避免 OCR、官网排版或解析器升级产生伪变化。

旧变更记录如能在 Git 中找到前后两版演出详情，可补录快照：

```bash
npm run changes:backfill -- <before-revision> <after-revision> [detected-at]
```

- 标题、日期、时间、城市、场馆和厅堂。
- 票价、状态、购票链接、来源链接和采集时间。
- 乐团、指挥、演奏者、作曲家和标签。
- 作品、作品号、乐章、作词/编曲/改编等节目单署名以及字段置信度。
- 数据质量状态：`scraped`、`manual-reviewed`、`ocr-assisted`、`ai-enhanced` 或 `needs-review`。

## OCR

只有同时满足以下条件的图片型详情页才执行图片识别。当前包括东方艺术中心、星海音乐厅、深圳交响乐团、深圳音乐厅、中山公园音乐堂和西安音乐厅：

1. 页面正文没有解析出曲目。
2. 详情内容包含图片。
3. 项目没有可复用的 OCR 缓存。

已有文字节目单的页面不会扫描图片，避免把乐团照片、人物照片和简介海报误当成节目单。普通采集会初扫全部符合条件的项目，每个项目最多检查 3 张图片；`scrape:ocr` 最多检查 8 张。

```bash
npm run scrape
npm run scrape:ocr
npm run scrape:no-ocr
```

配置交大 AI 接口后，图片优先交给 `qwen3.6-27b` 精确转写，再进入各来源自己的节目单解析器；鉴权失败、超时、限流、模型异常或输出校验失败时，同一次采集会自动加载 Tesseract `chi_sim` 模型继续处理。图片按内容哈希、模型和提示词版本缓存，即使官网复用同一 URL 更换图片也不会沿用旧结果；项目级结果默认 7 天刷新一次。可以在 `.env` 中配置：

```text
SHOAC_OCR_MAX_NEW_PROJECTS=
SHOAC_OCR_MAX_IMAGES=3
SHOAC_OCR_MIN_CONFIDENCE=55
SHOAC_OCR_MIN_PROGRAM_ITEMS=2
SHOAC_OCR_CACHE_MAX_AGE_DAYS=7
SHOAC_OCR_PROJECT_IDS=
```

- `SHOAC_OCR_MAX_NEW_PROJECTS`：可选的单次新增项目上限；留空时处理全部符合条件的项目。
- `SHOAC_OCR_MAX_IMAGES`：每个项目最多识别的详情图片数。
- `SHOAC_OCR_MIN_CONFIDENCE`：按文字量加权后的最低平均置信度。
- `SHOAC_OCR_MIN_PROGRAM_ITEMS`：至少解析出的可信曲目数。
- `SHOAC_OCR_CACHE_MAX_AGE_DAYS`：项目级结果的刷新周期。
- `SHOAC_OCR_PROJECT_IDS`：只调试指定项目，多个 ID 使用英文逗号分隔；留空时自动处理缺少文字节目单的项目。

处理顺序固定为：官网文字优先 → OCR 图片 → 清洗常见空格与分隔符 → 当前来源专用节目单解析器 → 标题、平均置信度和最少曲目数质量门槛。无论是否通过自动门槛，OCR 都只生成审核候选，不直接写入面向用户的正式节目单。识别原文、图片、置信度和拒绝原因保存在本地检查报告及审核队列中。其他图片型来源每个项目默认最多检查 3 张图，可用 `OCR_MAX_IMAGES` 调整。

对于正文和 OCR 都未能提供足够节目单信息、但已经留下 OCR 证据图片的演出，详情页会折叠展示原始图片并支持放大查看；图片按需加载，不增加首页数据和首屏请求。已有可信文字节目单时不展示这组兜底图片。

### 人工审核

审核工作台只在本地开发环境开放，并要求已登录账号在 `user_roles` 中具有 `admin` 角色。使用 `npm run dev` 启动本地服务后，以管理员账号点击页面顶部“审核”，或打开：

```text
http://127.0.0.1:5173/?review=1
```

审核页提供待审核列表、官网原图、OCR 原文和结构化曲目编辑器。可以逐首修改曲名、作曲家、作品号和英文/其他原文名，然后：

- **确认节目单**：写入 `data/manual-reviews.json`，曲目置信度改为 `manual`，数据状态改为 `manual-reviewed`。
- **驳回候选**：记录驳回结果，不把 OCR/AI 曲目写入正式节目单，也不再重复进入审核队列。

保存后本地 API 会立即重建静态数据和 SQLite。人工决定使用稳定演出 ID 与来源记录匹配，之后重新采集时会自动重新应用。`data/manual-reviews.json` 应提交到 Git，OCR 图片、模型和原文缓存不提交。

跨来源合并时采用 `人工 > 官网 > OCR > AI > 标题推断` 的字段优先级。场馆或乐团官网提供正式节目单后，OCR 不会覆盖它。

### 公众号半自动导入

本地启动后进入“审核 > 公众号导入”。可以只粘贴 `https://mp.weixin.qq.com/s/...` 链接；如果微信返回验证页或空正文，同时粘贴文章正文即可继续。系统会按日期区块生成一场或多场候选，并初步提取城市、场馆、时间、票价、乐团、指挥、演奏者、作品、原文名和组曲乐章。

候选中的全部字段都可以修改。点击“确认并发布”后，结构化演出写入 `data/manual-events.json`，立即参与官网数据去重、变化检测、SQLite 重建和静态导出；点击“驳回候选”只记录本地决定。未经确认的候选不会进入正式数据。

公众号原文和收件箱保存在被 Git 忽略的 `data/wechat-inbox.json`，仓库只提交人工确认后的结构化字段。正式记录会显示具体公众号名称和“公众号人工导入”标记，并保留文章原链接。也可使用命令行导入：

```bash
npm run wechat:import -- --url "https://mp.weixin.qq.com/s/..."
npm run wechat:import -- --url "https://mp.weixin.qq.com/s/..." --text-file article.txt
npm run wechat:import -- --url "https://mp.weixin.qq.com/s/..." --text-file article.txt --ai
```

公众号规则解析不依赖 API。配置 `SJTU_AI_API_KEY` 后，审核页可显式勾选 AI 增强；旧的 `DEEPSEEK_API_KEY` 仍兼容。模型输出必须通过 Zod Schema，并且仍然只能进入待确认队列。

## AI 辅助采集与知识库

复制 `.env.example` 为 `.env`，填写：

```text
SJTU_AI_API_KEY=你的密钥
SJTU_AI_BASE_URL=https://models.sjtu.edu.cn/api/v1
SJTU_KNOWLEDGE_MODEL=deepseek-reasoner
SJTU_PROGRAM_MODEL=deepseek-chat
SJTU_VISION_MODEL=qwen3.6-27b
PROGRAM_AI_MAX_REVIEWS=30
```

然后运行：

```bash
npm run scrape:ai
npm run knowledge:dry-run
npm run knowledge:enrich -- --limit 1
npm run knowledge:enrich -- --limit 1 --force
```

`scrape:ai` 仍先运行每个网站的专用规则。规则结果缺失、重复、包含人物或署名泄漏等明显异常时，会由 `deepseek-chat` 对照带行号的官网原文复核；国家大剧院版式变化较多，所有存在节目文字的场次都会进入基础复核。AI 只能调整节目单结构；每个作品、作曲家和作品号都必须在引用原文或原解析中出现，否则整次替换作废。图片型节目单使用 `qwen3.6-27b` 转写后仍进入来源专用解析器。单次任务最多复核 60 场，连续三次接口失败后才停止本轮 AI 复核；任一 AI 接口不可用时，文字保留规则结果，图片回退 Tesseract，来源采集和 Pages 构建不会因此中断。

公众号导入仍进入审核队列；节目单复核和公众号导入不能自动创建知识。只有 `knowledge:enrich` 使用受控来源、身份解析、外部补证、完整生成、缺失字段补全、独立审计、严格 Schema 和确定性风险评分执行无人值守知识发布。`--force` 仅用于调试，会忽略基础条目的下一次补全时间。

线上只在 GitHub Actions 中读取密钥，前端和 GitHub Pages 均不会得到它。进入仓库 **Settings → Secrets and variables → Actions → Secrets → New repository secret**，新建名为 `SJTU_AI_API_KEY` 的 Repository secret。非敏感配置可在同页的 Variables 中按需添加 `SJTU_AI_BASE_URL`、`SJTU_KNOWLEDGE_MODEL`、`SJTU_PROGRAM_MODEL` 和 `SJTU_VISION_MODEL`；全部留空时使用上面的默认值。旧的 `DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL` 和 `DEEPSEEK_MODEL` 仅在未配置新密钥时作为兼容配置，不会覆盖交大接口地址和模型。

`knowledge-enrichment.yml` 每天独立运行一次，优先补全旧基础条目，再处理新作品，每次合计最多 5 部；验证通过后直接提交 `knowledge/` 到 `main`，随后触发常规 Pages 部署。若 `main` 开启了禁止 GitHub Actions 直接推送的保护规则，需要为该工作流配置例外。

- 哈尔滨音乐厅从经确认的项目 ID 请求麦座官方项目详情；当前只维护已确认的 3 场，不通过连续编号猜测不存在的演出。

数据来源页以“乐团 / 场馆”两个视图展示真实封面、名称、当前场次数、详细介绍和官网入口。封面与 Logo 均保存在仓库内，避免第三方防盗链导致线上空白。

北京交响乐团目前只发布乐季 PDF，待获得稳定的当季 PDF 地址后接入独立 PDF adapter。江苏大剧院公开网站证书异常，详情又由带动态签名的第三方票务接口提供；在无法稳定取得具体场次时间和节目单前，不发布仅有日期范围的猜测记录。

LocalHub 已退出正式数据源。它可以用于发现演出线索，但缺少稳定详情页和节目单，不应作为正式节目单来源。

## 自动部署

工作流位于 `.github/workflows/deploy-pages.yml`，执行顺序固定为：

1. 安装锁定依赖并运行 adapter、存储层测试。
2. 下载当前线上完整数据作为变更比较基线。
3. 从全部已配置来源重新采集。
4. 运行数据审计和 SQLite/静态导出一致性审计；失败来源必须有上一版数据可恢复，否则停止部署。
5. 使用 `/Classic-Music/` 基路径构建并部署到 GitHub Pages。

Pages 构建需要在仓库 `Settings > Secrets and variables > Actions` 配置 Supabase 项目 URL 与 Publishable Key。推荐放在 **Variables**，名称使用 `VITE_SUPABASE_URL` 和 `VITE_SUPABASE_PUBLISHABLE_KEY`；为兼容已有设置，工作流也读取 **Secrets** 标签以及不带前缀的 `SUPABASE_URL` / `SUPABASE_PUBLISHABLE_KEY`，并在构建时统一映射到 Vite 变量。它们本身是可公开的前端配置，但 Secret Key 或 Service Role Key 绝不能用于前端。发布前工作流会自动验证免确认注册、数据隔离和管理员权限；配置缺失或检查失败时会停止，避免发布一个登录入口不可用或权限配置不完整的版本。

本地验证 Pages 构建：

```bash
$env:VITE_BASE_PATH="/Classic-Music/"
npm run build
```

GitHub Pages 继续承载以读取为主的静态前端和数据文件，Supabase 提供账号身份、角色和个人数据同步。“想去/已购”、演出快照、关注、提醒状态与筛选方案只有登录后可用，并由私有表和 RLS 按用户隔离；浏览器缓存用于即时响应和离线兜底，不改变现有静态演出发布链路。

## 已知限制

- 目前配置 18 个来源，覆盖上海、北京、苏州、广州、深圳、杭州、西安和哈尔滨；中山公园音乐堂与哈尔滨音乐厅条目标明实际票务来源，不冒充场馆官网。
- 前台只展示未来演出；历史数据只作为本地 SQLite、完整 `events.json` 基线和变更检测输入保留。
- 当前跨来源合并采用高置信度保守规则；不确定候选尚无管理界面。
- 从节目文本生成的 `workId` 用于兼容现有实体关联，但会受译名和元数据修订影响；只有人工分配的 `knowledgeWorkId` 是长期稳定的规范知识 ID。
- 知识库目前发布 13 位作曲家和 50 部作品，其中 36 部人工维护、14 部自动整理。自动条目中 9 部达到完整详情结构，5 部因录音或其他证据不足保留为基础条目并进入持续补全队列。
- 前台已内置一批常见作品简称别名，但仍需继续补充不同中文译名、外文名和更多低频简称。
- 定时采集已部署，尚未接入邮件或即时通讯失败告警。
- SQLite 仍是构建期演出数据仓库；个人数据已跨设备同步，但公开演出与知识数据仍按静态快照更新，不提供用户自行编辑。
- 管理员角色已由后端 RLS 表控制，但 GitHub Pages 没有审核写入 API，因此正式站点不会开放远程审核操作。
- 公众号导入和审核目前只在本地开发服务中可写；微信链接遇到风控或验证页时需要粘贴正文。
- 自动知识任务采用保守阈值，证据较少的冷门作品会被跳过；同一 DeepSeek 模型的生成与复核不能等同于独立音乐学审校，因此页面明确标识自动整理和分数。
